# Architecture Decisions（2026-07-28）

## Request 定位

-   一封 Email = 一個 Request
-   一個 Request = 一個申請事項
-   一個 Request = 一個 Workflow

不考慮一封信拆成多個
Request，因不同申請通常有不同主管、審核流程與負責人。

## Request Content

Collector 解析、驗證並加工來源資料後，存入 Request.Content(JSON)。

Workflow 僅依 RequestType 解析 Content，不需知道來源是 Email、Web、API
或其他 Collector。

``` json
{
  "EmployeeId": "A12345",
  "StartDate": "2026-08-01",
  "Group": "Vendor"
}
```

## Collector 職責

-   收集來源
-   解析內容
-   驗證資料
-   加工資料
-   建立 Request

Collector 不執行業務流程。

## Workflow 職責

-   依 RequestType 執行流程
-   解析 Request.Content
-   執行自動化
-   更新 Request Status
-   寄送通知

Workflow 不修改 Request.Content，只更新狀態與結果。

## Request 生命週期

``` text
New
 ↓
Workflow
 ↓
Completed / Failed
 ↓
Notification
 ↓
End
```

Request 為一次性 Job，寄信完成後生命週期即結束。

## Version Policy

目前不規劃 Content Version。

若 VPN 或其他流程需求改變，直接調整 Collector 與
Workflow，不為未發生的問題增加設計複雜度。

## 初版策略

先完成： - Email Collector - Request - Large File Workflow - Status
更新 - Notification

先驗證核心架構，再擴充第二個 Workflow。

## 設計哲學

-   Request 像海，容納百川。
-   Collector 像河川，將不同來源轉換為統一 Request。
-   Workflow 依 RequestType 執行，不依賴來源。
